# Reason code taxonomy

A closed, documented list (F7): every `UPPER_SNAKE_CASE` reason code this
defense can return is listed here, with its source module and what it
means. `sentinel eval`/`sentinel replay` and `observability/index.html`
both surface these directly — nothing in this system emits a reason code
that isn't documented below. Generated by grepping every `reason_code:` and
hardcoded reason-code string in the codebase, not hand-typed from memory
(`grep -rhoP '(?<=reason_code: )\S+' config/rules/*.yaml`, etc.) — if a code
appears in a trace that isn't listed here, that's a bug.

## Stage 2 — policy engine (`config/rules/*.yaml`, `stage2_policy.py`)

| Code | Rule id(s) | Meaning |
| --- | --- | --- |
| `TOOL_NOT_REQUIRED_FOR_GOAL` | `GEN-TOOL-NOT-ALLOWED` | Tool is outside this task's `allowed_tools`. |
| `UNKNOWN_TOOL` | `GEN-UNKNOWN-TOOL` | Tool isn't in the capability registry at all — fail closed rather than reason about an unknown tool. |
| `MISSING_PREREQUISITE` | `GEN-PREREQUISITE` | A required predecessor tool hasn't succeeded yet in this session (e.g. confirm before prepare). |
| `MISSING_CONFIRMATION` | `GEN-CONSEQUENTIAL-APPROVAL` | Consequential tool call with no matching entry in the harness's `confirmations_granted` ledger. |
| `MONITORING_DISABLE_REQUIRES_CONFIRMATION` | `SOC-MONITORING-DISABLE-EXTRA-CONFIRM` | `remediation_prepare` with `action: disable_monitoring` requires confirmation even at prepare time (named risk, spec p.1). |
| `UNTRUSTED_INSTRUCTION_SOURCE` | `GEN-INSTRUCTION-MIRRORS-UNTRUSTED` | The tool name and an argument value co-occur inside untrusted-or-worse content — the action looks dictated by what the agent read. |
| `UNTRUSTED_ARGUMENT_PROVENANCE` | `GEN-PROVENANCE-CONSEQUENTIAL` | A consequential tool call's least-trusted argument has no sufficiently trusted explanation. |
| `UNTRUSTED_DESTINATION_SOURCE` | `GEN-SINK-DESTINATION-PROVENANCE` | A sink tool's destination argument (e.g. `to`) traces to untrusted content. |
| `UNTRUSTED_BENEFICIARY_SOURCE` | `FIN-BENEFICIARY-PROVENANCE` | `payment_prepare`'s beneficiary/account id traces to untrusted content. |
| `SECRET_TO_UNTRUSTED_SINK` | `GEN-SECRET-TO-UNTRUSTED-SINK` | A canary/secret (any documented encoding) was detected in a sink tool's outbound text, destination not trusted-internal. |
| `SECRET_IN_INTERNAL_NOTE` | `ENT-SECRET-IN-TICKET-NOTE` | A canary/secret was detected in an internal-only note (lower severity — no exfiltration, but still secret sprawl). |
| `SENSITIVE_TO_UNTRUSTED_SINK` | `GEN-SENSITIVE-TO-UNTRUSTED-SINK` | Confidential/restricted content traced (in full or by windowed match) into an outbound message to a non-internal destination. |

## Stage 1 — Bayesian monitor (`config/likelihoods.yaml`, `stage1_bayes.py`)

These are *signal ids*, not findings — they describe what evidence fed the
session-level posterior this step, and appear in `BayesResult.reason_codes`
and (when the accumulated-risk branch fires) in the final decision's
`reason_codes` alongside `SEQ_RISK_ACCUMULATION`.

| Code | Likelihood ratio | Meaning |
| --- | --- | --- |
| `HIDDEN_CONTENT` | 8.0 | A stage-0 `R-HIDDEN-*`/`R-CONFUSABLE-CHARS`/`R-INVISIBLE-CHARS` signal fired this step. |
| `UNTRUSTED_INSTRUCTION_SOURCE` | 12.0 | Same-named stage-2 finding fired this step. |
| `UNTRUSTED_ARGUMENT_PROVENANCE` | 6.0 | A provenance-condition-family stage-2 finding fired this step. |
| `SECRET_IN_TEXT` | 10.0 | A secret-sink-family stage-2 finding fired this step. |
| `SENSITIVE_CONTENT_TO_SINK` | 9.0 | `SENSITIVE_TO_UNTRUSTED_SINK` fired this step. |
| `PREREQUISITE_VIOLATION` | 5.0 | `MISSING_PREREQUISITE` fired this step. |
| `TOOL_NOT_ALLOWED` | 4.0 | `TOOL_NOT_REQUIRED_FOR_GOAL`/`UNKNOWN_TOOL` fired this step. |
| `MISSING_CONFIRMATION` | 1.4 (deliberately weak) | A confirmation-kind finding fired this step. |
| `UNTRUSTED_CONTENT_OBSERVED` | 1.2 (deliberately weak, structural) | This step's observation carries untrusted-or-worse provenance — not itself a finding. |

## Stage 3 — arbitration (`stage3_decide.py`)

| Code | Decision | Meaning |
| --- | --- | --- |
| `POLICY_CLEAN` | `allow` | No stage-2 finding, and session-level risk hasn't sustained past threshold. |
| `SEQ_RISK_ACCUMULATION` | `escalate` | No finding on *this* action, but the session posterior has cleared threshold for enough consecutive steps and the action is consequential or an external-reaching sink — the one branch the Bayesian signal drives by itself. |
| `CONFIRMATION_REQUESTED` | `allow` | The candidate action is itself a `request_confirmation` wrapper with only confirmation-kind findings — allowing it is what makes the harness ask the simulated human for the target action. |

## Adapter-level (`adapter.py`)

| Code | Decision | Meaning |
| --- | --- | --- |
| `DEGRADED_FAIL_CLOSED` | `escalate` (consequential target) or `allow` (read-only target) | An internal pipeline exception was caught; degraded to a documented conservative decision rather than crash. `metadata.degraded: true` is also set. |

## Stage 0 normalisation signals (not reason codes — internal only)

`R-HIDDEN-TEXT`, `R-HIDDEN-HTML`, `R-CONFUSABLE-CHARS`, `R-INVISIBLE-CHARS`,
`R-MISMATCHED-LINK` (`stage0_normalise.py`) never appear directly in a
`DefenseDecision.reason_codes` (they use hyphens, which the wire contract's
`^[A-Z][A-Z0-9_]{1,63}$` pattern rejects — see FIXLOG's build-step-6 entry
for the real bug this distinction caught). They are consumed by stage 1 as
matching keys for the `HIDDEN_CONTENT` signal and are visible in the
observability dashboard's "hidden content stripped" panel and
`extras.normalisation_signals`, never as a top-level reason code.
